Design Authority · worked example — “Jennu” (packs/phantom 0.2.0)

A design authority: what it looks like,
and how it versions & evolves

A design authority is a versioned, machine-readable description of an interface system — its components, rules and fallbacks — written so that two independent readers can use the same contract: a coding agent that builds with it, and a verifier that checks whether the build actually conforms. It is a contract, not a style guide.

01What it looks like — the pack

packs/phantom/ — the authority pack (v0.2.0, named Jennu)
├─ authority.json identity · snapshot · version
├─ artifacts.json 29 records — 6 token-sets · 1 guideline · 17 components · 5 layouts
├─ rules.json 8 — P-R1 reading-ink-pink … P-R8 state-colour-pink
├─ prohibitions.json 2 — e.g. “don’t rely on accent ink below 3:1”
├─ fallbacks.json 4 — light-only · no-script · cjk-system-fallback …
├─ precedents.json 1 — adjudications that persist across versions
├─ candidates.json 3 — ambitions with an explicit promotion bar
├─ golden.json 21 cases — ask → expected outcome (guards resolution)
├─ recipes.json 0 — compositions, once they exist
└─ verification.json 15 checks — the conformance contract

Plain JSON — no database. Records a consumer produces (resolutions, gaps, proposals) are written to the consumer’s own workspace, never back into the pack; only adjudicated decisions move the pack forward.

How a consumer reads it

“a primary button”resolved →component/action-button
“a carousel with controls”undefined →candidate surfaces a bar: sources, motion policy, controls
“CJK in the wordmark”fallback →constraint recorded (no CJK stack declared)

02How it versions & evolves

A real revision — the redo

  • v0.1.0 initial freeze — hashed, git-tagged

    Extracted from the template’s stylesheet: grey ink canon, the site’s pink type misfiled as “deviations”. Verified mechanically (its contract re-run clean: 17/17), but extracted from the wrong layer.

  • rejected owner review of the rendered result

    “The site that exists runs pink type — extract what IS.” A version can be internally consistent and still describe the wrong thing; only rendered evidence settles it.

  • v0.2.0 fresh freeze — all pack files re-hashed

    Re-extracted screenshot-first (4 domain teams, 64 captures): canon = the deployed language. The reversal became precedent/pink-ink-canonised — the old decision is superseded, not deleted. Goldens re-run 21/21; the verification contract rewritten (15 checks) and re-run 15/15.

The standing rules

Editorial edit → patch bumpWording, typos, clarifications. No re-freeze needed.
Semantic change → minor bump + fresh freezeNew/changed records, pipeline order, thresholds, tool contracts, governance taxonomies.
Adjudications become precedentsAccepted / declined decisions persist across versions so agents never relitigate them.
Ambitions become candidatesEvery candidate carries an explicit promote-when bar — no silent canonisation.
Friction is recorded, not smoothedConsumer gaps are filed per workspace; resolutions and proposals are first-class records.
The contract co-versionsGoldens guard resolution; the verification contract travels with the pack and re-runs against every build.

The evolution loop

extract (rendered evidence) → freeze (hashes) → consume (agents resolve & build) → verify (independent checks) → adjudicate (precedent · gap · candidate) → next version → consume again. Nothing moves the pack except an adjudicated decision.
