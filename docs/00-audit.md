## 2. Layer-by-layer findings

### 2.1 Foundations & tokens
- One source of truth (`tokens.json`), one generated CSS (`tokens.css`), one
  governance rule ("every emitted token must have a consumer or a documented
  reason", enforced by `tools/token_map.py` against `spec/token-consumers.json`
  + `spec/token-metadata.json`). This is unusually disciplined.
- **Tiers:** primitives (`--acc`, `--fg`, `--line` …) → semantic aliases
  (`--surface-*`, `--text-*`, `--status-*`, `--interactive-*`) → consumed by
  components. TDS012 makes primitive use in products a (warning) offence when an
  alias exists — the alias tier is what makes retheming safe.
- **Themes:** light default, dark via `data-theme="dark"` and
  `prefers-color-scheme`. **Density:** comfortable default, compact via
  `data-density="compact"` (`--base-size` 1rem → 0.9375rem; per-token
  `com.triage.compact` extensions). **Motion:** 9 durations + easing tokens
  (TDS006). **Breakpoints** in `misc.breakpoint`, substituted into media
  queries at compose time (`{bp-phone}` etc.). **Z-index ladder** (TDS007).
  **Radius policy = 0**, enforced globally (`*{border-radius:0 !important}`,
  TDS003). **Dataviz:** Okabe-Ito derived `--dv-1..8` + CVD guidance, reserved
  for downstream chart code (no chart components ship).
- Spacing: curated preferred scale (2/4/8/12/16/24/32/48) + semantic roles
  (`--space-page/card/field/control`) + `--layout-*` for fixed chrome widths;
  legacy steps remain emitted, labelled legacy.

### 2.2 Components
- `spec/states.json`: **35 components** (`btn`, `iconbtn`, `px-sw`, `menu-item`,
  `nav-item`, `chip`, `index-row`, `tbl`, `bulkbar`, `savebar`, `msg`, `toast2`,
  `badge`, `empty`, `dlg`, `tip`, `spinner`, `field-err`, `tabs`, `crumbs`,
  `radio`, `slider`, `cb`, `dp`, `acc`, `avatar-sq`, `img`, `drop`, `notif`,
  `cmd`, `page-state`, `pager-num`, `tl`, `diff`, `sheet-end`). Each carries
  `states`, `verify` selectors (checked against core CSS by `tools/verify.py`),
  `a11y` notes, and `status` (currently all `stable`; lifecycle definitions
  state what evidence each status requires — stable means behavioural coverage
  in `tests/browser/`, not selector presence).
- JS: 9 families need `components.js` (tabs, combobox, datepicker, command
  palette, dropzone, notifications, sortable tables, slider); `shell.js` (toast,
  arm-delete, copy, drawer, menus); `app.js` (markdown renderer, chat engine,
  view transitions); `keyboard-fit.js`; `i18n.js`. Everything else is CSS-only
  and degrades to plain markup without JS.
- **Class inventory reality check:** `core/base.css` + `core/patterns.css`
  define **428 classes**. Only 35 are registered as components; the rest are
  sub-elements, state modifiers, utilities, and pattern classes. The examples
  use 261 classes, of which only 4 (`demo-*`, showcase chrome) are not in the
  system. So the catalog is *nearly closed* in practice — but only 35 of 428
  names carry any formal registration.

### 2.3 Patterns & page conventions
- Patterns (dashboard, detail, settings, flows, dry-run, stepper, index/eval)
  exist as: CSS sections in `src/core/patterns.css` (with provenance comments),
  prose on `site/pages_patterns.py` pages, and example screens. They are **not**
  in `states.json` and have no verify/states/a11y entries — nothing
  machine-readable registers them.
- Page/screen conventions observable in examples and CSS: app shell (fixed
  236px sidebar with grouped nav + brand + status footer; mobile topbar +
  bottom tab bar ≤767px; optional docked chat), page-head (title/desc/actions),
  cards with `.card-h` headers, hero stat strips (tabular-nums), stacked feeds
  (`.mfeed`), tables (`.tbl`, phone collapse via `.tbl.mcards`), row actions
  (`.rowacts` with `.ra-inline`/`.ra-menu`), selection toolbar (`.bulkbar`),
  editors ending in `.savebar`, empty states (`.empty` anatomy), queue bars,
  log/terminal panels. Some are normative in `INTERACTION.md`; many are only
  visible in examples.
- Page hierarchy contract (page title → section heading → card heading → body →
  meta + tokens per level) lives on the typography docs page — prose, not spec.

### 2.4 Navigation
- Shell conventions documented via example + patterns + mobile references:
  sidebar groups, active rail, off-canvas drawer ≤1023px, bottom tab bar ≤767px,
  skip link, scrim. No standalone "navigation contract" document; the shell
  example is the de-facto template ("This IS the file to start from for a port").

### 2.5 Feedback
- Strictly defined in `INTERACTION.md`: redirect → `.msg` banner (kinds exactly
  `ok|warn|err`; no info kind); in-place → `toast()` (`.toast2`, same three
  kinds); every mutation announces (past tense, names the object); auto-submit
  controls must announce. Field errors via `.field-err` with focus summary.
  This is one of the most rigorous parts of the system.

### 2.6 Responsive behaviour
- Breakpoints tokenised; core queries use placeholders. Phone behaviour rules
  are component-by-component (tab bar, drawer, card-collapse tables, 44px
  coarse-pointer targets, keyboard-fit for on-screen keyboards, 100dvh,
  safe-area insets). Width matrix + density/theme matrix tested in
  `tests/browser/` (exact viewports via iframes; UI baseline at 1440/390 ×
  {light-comfortable, dark-comfortable, light-compact}).

### 2.7 Accessibility
- Global `:focus-visible` ring (TDS004 protects it). Per-component a11y notes
  in `states.json`. Lint covers alt text (TDS014), accessible names +
  positive tabindex (TDS015), contrast of defined token pairs (TDS011).
  Browser suite checks contrast regressions + interaction (keyboard) fixtures.
  `INTERACTION.md` sets label/touch-target/colour-not-alone rules; dataviz page
  carries CVD guidance. A single consolidated WCAG-level requirement matrix
  does not exist — requirements are distributed across lint + prose + notes.

### 2.8 Content / copy conventions
- `/foundations/voice` page + `INTERACTION.md` (sentence case; name the object
  in destructive labels; Enable/Disable verbs, never Pause/Resume; announcement
  wording; the exceptions register). Copy guidance is example-based prose;
  almost none of it is lint-checkable, and none is machine-readable.

### 2.9 Explicit do/don't guidance
- Present but scattered: typography page (page-hierarchy do/don'ts), colour
  page (ink literals, tint pairings, "do not theme by overriding components"),
  dataviz (colour-not-alone), brand page (white-label checklist), README
  (load order), INTERACTION.md (exceptions register, review checklist).
  There is no single normative do/don't catalogue; `rules.json` is the only
  consolidated normative list, and it covers only what lint can check.

### 2.10 Enforcement & quality gates (what ships today)
- `lint/triage_lint.py`: 15 rules (TDS001–TDS015) with stable IDs, severities
  (error/warning/info), `why` + `fix` text; per-project `.triagerc.json`
  overrides + ignore globs; inline suppressions (`triage-allow TDSxxx`,
  `triage-disable-file`); `--json` machine report (findings with file/line/
  message/excerpt/fix, counts, per-rule summary, spec score). The repo
  dogfoods at 100/100 across 46 files; CI fails on any error.
- `tools/verify.py` (DTCG validity, alias cycles, token sync, rename sweep,
  rule↔implementation parity), `tools/token_map.py --check` (consumption
  contract), browser suite (10 fixtures, 248 assertions incl. UI baseline
  drift), `tools/metrics.py` (compliance history), `tools/package.py`
  (verified tarball).
- Culture evidence: `site/AUDIT.md` records the original pack audit and the
  four-reviewer adversarial pass with a findings register; recent branches
  were driven by an adversarial-reviewer agent loop with mutation evidence
  (see `/tmp/opencode/fix-closure.md`); releases are stamped (VERSION ⇄
  package.json ⇄ docs chrome) and changelogged.

## 3. Classification: A (explicit authority) / B (inferable) / C (undefined)

### A · Already explicit authority
1. **Tokens** — machine-readable values + tiers + density/theme variants
   (`tokens.json`, `tokens.css`, `spec/token-consumers.json`,
   `spec/token-metadata.json`).
2. **Lint rules** — machine-readable, citable, severity'd, fix text (`spec/rules.json`),
   implemented (`lint/engine.py`), testable (`lint/tests/`).
3. **Component lifecycle/states/a11y** — machine-readable (`spec/states.json`)
   + selector verification (`tools/verify.py`).
4. **Vocabulary** — rename authority (`rename-map.json`, RENAME-MAP.md).
5. **Interaction standard** — binding prose with an exceptions register
   (`INTERACTION.md`), partially enforced by lint.
6. **Enforcement mechanics** — lint CLI with JSON output; suppressions;
   per-project config; CI gates; token map; browser/contrast/UI baseline.
7. **Reference screens** — 7 real example pages.
8. **Human docs** — foundations/components/patterns/spec pages (rendered from
   shipped artifacts).
9. **Governance for the repo itself** — `AGENTS.md` (generated files, gates,
   provenance, breaking-change policy).

### B · Inferable (present, not formalised)
1. The full class/sub-element/state vocabulary (428 classes) — derivable by
   parsing CSS; only 35 names are registered.
2. Patterns (7 documented, 149 CSS classes) — derivable from
   `src/core/patterns.css` + examples + docs pages; nothing registers them.
3. Page/screen anatomy conventions (page-head, cards, feeds, hero strips,
   queue bars, log panels …) — visible in examples + pattern CSS.
4. Responsive specifics per component (what hides/reflows at which width) —
   in CSS comments + mobile docs + tests, not consolidated.
5. "When to use X vs Y" guidance — spread across docs pages and example usage;
   some in `states.json` a11y notes.
6. Copy/voice conventions — prose examples, not rules with IDs.
7. Do/don't guidance — distributed; only lint-checkable parts are normative.
8. JS behaviour contracts — `provenance/references/js-behaviors.md` (a pack
   reference), not part of the spec layer.
9. Severity-override semantics (what a project may switch off and what that
   means for conformance) — implied by `.triagerc.json`, not formalised.

### C · Genuinely undefined / ambiguous (gaps)
1. **No composition layer.** `INTERACTION.md` references sanctioned
   compositions (armed delete, toggle + announcement, bulk bar + selection,
   empty + single CTA) but they are prose patterns with no machine-readable
   "recipe" concept. "Compose from existing artifacts" cannot be resolved
   mechanically today.
2. **No fallback tier.** There is "system" and "off-system", nothing between.
   A sanctioned generic fallback ("plain text + tokens", "native element with
   system classes") is not expressible, so downstream agents either comply or
   fork — with no middle ground to certify.
3. **Patterns are second-class.** The docs present patterns as equals of
   components, but only components carry states/verification/a11y data.
   The component↔pattern boundary is undefined ("page-state" is a component,
   "dashboard" is a pattern — why?).
4. **Async/long-running work UI is undefined.** Components cover `spinner`,
   `page-state`, a Button "busy" state, and log panels; there is no canonical
   treatment for *progress of a background job* (indeterminate vs determinate,
   where it lives, how it reports failure). This is exactly the kind of hole
   the benchmark briefs probe.
5. **Underspecified requests have no protocol end-to-end.** Nothing in the
   repo tells a consuming agent what to do when the system lacks an answer:
   no "mark improvisation", no gap record, no proposal route. (AGENTS.md
   governs agents *inside* the repo; consumers have nothing.)
6. **Copy rules are not enforceable**, and the voice page's examples are not
   tied to rule IDs — copy can drift without tripping any gate.
7. **A11y requirements lack a consolidated matrix** (per component they exist;
   system-wide WCAG claims are references in prose).
8. **Charts/data-viz**: tokens + guidance exist; no components/patterns;
   explicitly "consumed by downstream chart code" — an acknowledged hole.
9. **Multi-brand / white-label boundary** (theming vs forking) is prose
   (brand page + TDS009/TDS012 semantics); no formal "brand overlay" spec.
10. **Conformance levels.** What does "on-system" mean for a product that
    disables TDS005 via `.triagerc.json`? No formal definition of acceptable
    project variation exists.
11. **Extension/contribution protocol for downstream products** — absent by
    design so far (the repo is the workshop; consumers only read).

## 4. What can already function as authority (assessment)

Triage is ~70% of a machine-readable authority *today*: values, rules,
component state contracts, and enforcement are all structured and citable.
The missing ~30% is exactly the kernel's scope:

| Authority concept | Triage today | Gap to close |
|---|---|---|
| Values | `tokens.json` + generated CSS + consumption contract | expose as artifacts; search aliases |
| Rules | `rules.json` + engine + severities + fixes | expose; map to validators; default overrides per project |
| Components | `states.json` (states/verify/a11y/status) | join with class inventory + docs + examples into artifacts |
| Patterns | docs pages + CSS sections | register as artifacts (kind-agnostic kernel handles this; Triage defines kind) |
| Compositions | prose in INTERACTION.md | extract sanctioned recipes |
| Fallbacks | none | define tier + policy |
| Resolution | none | search + outcome semantics |
| Validation | lint (+ browser suite) | validator-runner adapter; normalized findings |
| Gaps / proposals | none | gap store + noncanonical proposal flow |

Consequence for the plan: **the kernel must be thin**. Most of the "authority"
is a *packaging and indexing* exercise over already-structured files, plus a
small set of genuinely new concepts (resolution outcomes, recipes, fallbacks,
gaps, proposals). Anything that re-models tokens or re-invents the lint engine
is discarded by default.

## 5. Trajectory & version state

- 0.1.0 → 0.12.1 in five days of heavy agent-assisted work with adversarial
  review at each release (0.3.0: four independent reviewers; 0.11–0.12: scoped
  bundle, reset contract, review closures). The system is fast-moving.
- The prototype must **pin an immutable snapshot** (`e374f38`) and record it in
  the pack manifest. Upstream drift after that point is a threat to validity
  and, later, an opportunity for the re-run loop (Part 10).
- The lint engine, `states.json` schema, and token model are the most stable
  interfaces; docs pages and the shell example churn most.

## 6. Limitations of this audit

1. Read-only: no CI/browser gates were executed here; behavioural claims cite
   tests and recorded results, not fresh runs.
2. Docs site inspected via sources + route inventory + spot reads; not read
   page-by-page.
3. `states.json` status claims (all 35 `stable`) were not re-verified against
   the browser suite.
4. Counts (classes, tokens, rules) are exact for the pinned snapshot; they will
   drift as upstream advances.
5. This audit covers structure and authority-readiness, not visual quality —
   visual quality is the benchmark's concern, not the audit's.
